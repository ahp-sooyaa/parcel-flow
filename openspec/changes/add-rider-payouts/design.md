## Context

The app already has `financial_items` and `rider_payouts` tables, a placeholder `/dashboard/rider-payouts` page, and a validation-only rider payout action. Current delivery behavior creates `rider_way_payout` on successful delivery, while the new rule pays one way for the real delivery attempt even when the receiver delivery fails and the parcel is later postponed or returned.

The same parcel can now produce more than one rider way: one rider can earn the failed delivery attempt, another rider can later earn the merchant return, and retry attempts can earn additional ways. The current parcel-level `rider_payout_status` field is too coarse to be the source of truth for eligibility; `financial_items` must drive payout selection.

## Goals / Non-Goals

**Goals:**

- Represent each payable rider way as one `financial_items` row with `item_type = rider_way_payout`, `amount = 1`, and the rider assigned at the qualifying event time.
- Create delivery attempt way credits when an assigned rider starts delivery from `at_office` to `on_the_way`.
- Preserve failed attempt credits when admins resolve failure to `postpone` or `canceled_returned`.
- Create return way credits when an assigned rider completes merchant return work from `canceled_returned` to `returned_to_merchant`.
- Replace rider payout stubs with database-backed eligibility, draft creation, listing, cancellation, and super admin payment resolution.
- Keep merchant settlement and rider payout item selection independent even when generated by the same parcel lifecycle.

**Non-Goals:**

- No automatic weekly or monthly rider payout scheduling.
- No new `rider_payout_items` join table; selected items continue to link through `financial_items.rider_payout_id`.
- No retroactive reconstruction of missing failed-attempt credits from historical data.
- No change to COD handover timing or merchant settlement creation rules.

## Decisions

1. Use `financial_items` as the rider way event ledger.

   Each qualifying event inserts one `rider_way_payout` row. Multiple active rider way rows for the same parcel are allowed because retries and merchant returns are separate payable events. Add source metadata to `financial_items` for rider way rows so new rows can distinguish `delivery_attempt` from `merchant_return`; existing rider way rows can be migrated to a legacy delivery source. Eligibility queries filter by `item_type = rider_way_payout`, `status = pending`, `rider_id`, and `rider_payout_id IS NULL`.

   Alternative considered: calculate ways from current parcel status. This fails for postponed failed attempts, reassignment, and return work by a different rider.

2. Create delivery attempt credits at `Start Delivery`.

   `startDeliveryForRiderParcels` will lock selected parcel rows, confirm they are still assigned to the acting rider and `at_office`, change them to `on_the_way`, write status logs if the existing workflow requires them, and insert one pending `rider_way_payout` per parcel for that rider. `Mark Delivered`, `Report Failure`, and admin failure resolution do not create another delivery attempt item.

   Alternative considered: create rider way items on `Mark Delivered` and `Report Failure`. That splits one business rule across multiple outcomes and still misses attempts that are later resolved without an explicit failure payout path.

3. Create return credits at return completion.

   `markRiderParcelReturnedToMerchant` will keep creating the merchant `delivery_fee_deduction` item and will also insert one pending `rider_way_payout` for the rider assigned to the return at completion time. If an admin manually corrects or completes a return without an assigned rider, it creates the merchant deduction but no rider way unless the admin explicitly supplies a target rider in a correction flow.

   Alternative considered: credit the rider who attempted the failed delivery when the parcel is later returned. That conflicts with the assignment rule: the return way belongs to the rider assigned to the return work.

4. Treat rider way ownership as historical.

   A later assignment must not move already-earned historical way rows to the new current rider. A status correction does not create a missing delivery-attempt event; it requires an existing delivery-attempt item and preserves that item when its rider is already correct. When a status or rider correction also fixes the rider who performed the latest attempt, only that latest pending, unreserved attempt item is reassigned. Earlier attempts remain historical. In-progress or settled rider payout items continue to block unsafe ownership corrections.

   Alternative considered: update all parcel `rider_way_payout` rows whenever `parcels.rider_id` changes. That would pay the wrong rider in failed-attempt and return-by-different-rider cases.

5. Keep `parcels.rider_payout_status` as a denormalized display hint.

   Payout eligibility and totals use `financial_items` directly. After payout draft, cancel, or settlement changes, recompute each affected parcel's `rider_payout_status` from active rider way items: `pending` while any active item remains pending, `in_progress` while any active item is reserved and none are pending, and `settled` only when all active rider way items are settled.

   Alternative considered: remove use of `rider_payout_status`. That would be cleaner long term but is broader than this change and may disrupt existing parcel UI.

6. Mirror merchant settlement workflow for payout management.

   `/dashboard/rider-payouts` should list persisted payout records. The create flow uses a shadcn right-side sheet: select a rider with eligible pending way items, review/select items, enter `feePerWay`, show selected way count and total, and generate an in-progress payout. Payment resolution is super admin-only and marks the payout and linked financial items as settled.

   Alternative considered: keep a freeform delivered-way count. That is faster but breaks traceability to the financial items that prevent double payment.

## Risks / Trade-offs

- Duplicate way credits from repeated submits -> Lock parcel rows during qualifying transitions and insert only after the status eligibility check passes in the same transaction.
- Coarse parcel payout status can be misleading with multiple rider way rows -> Use financial items as the source of truth and recompute the parcel field only as a summary.
- Existing delivered way rows created before this change do not identify whether they came from delivery success -> Migrate them to a legacy delivery source, keep them eligible, and do not backfill missing failed attempts.
- Correction behavior can accidentally void earned attempt credits -> Update correction rules to preserve historical credits and block changes touching reserved or settled payout items.
- Correction behavior can accidentally invent payable work -> Require an existing delivery-attempt item when correcting to delivered instead of creating one from the corrected status alone.
- Eligible item queries may grow over time -> Add focused indexes on `financial_items` eligibility fields only if query performance requires it during implementation.

## Migration Plan

- No new backend service or dependency is required.
- Add a Drizzle migration for rider way source metadata on `financial_items`.
- Existing active `rider_way_payout` rows remain eligible for payout and should receive the legacy delivery source during migration.
- No data backfill is required for previous failed attempts because the system did not previously capture enough reliable event data.
- If implementation adds indexes, create them through a Drizzle migration and keep the table shape compatible with existing data.

## Open Questions

- The fee per way remains manually entered per payout draft for this change, matching the existing DTO. A future change can move it to a configured rider or township rate if needed.
